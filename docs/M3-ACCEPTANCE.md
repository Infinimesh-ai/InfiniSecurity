## 首轮失败与修正

第一轮 ① 未触发:fixture 每个项目只造了 40 个文件,而速率阈值默认 50。
测试设计的问题,不是实现问题。但这一轮意外验证了一条关键设计:那 40 次
删除**全部被 T2 二审拒绝**(fixture 不在 git 仓库里,无二审后端 →
fail-closed),A 项目一个文件都没丢,而 ③ 的广度维度照样正常触发——
证明"爆发检测在判决之前记账、被拒绝的删除同样计入"确实生效。
一个次次被拒却仍在疯狂尝试删除的进程,正是最该冻结的那种。

## 设计要点(与 PLAN 2.5 的对应)

- **冻结不是杀死**:SIGSTOP 保留现场与 pending syscall,人工可 SIGCONT
  恢复;SIGKILL 会丢掉正在进行的操作,断了后路。
- **不依赖二审**:纯本地滑动窗口计数,不调用任何可能超时的外部组件。
  要在最坏的时刻起作用的东西,不能依赖会超时的东西。
- **判决之前记账**:见上文首轮失败的说明。
- **叶子优先冻结**:先停子进程再停父进程,避免父进程在被停之前又
  fork 出新的删除者。
- **广度的计数单位是"项目"**:`~/Documents/A` 与 `~/Documents/B` 必须
  可区分,否则一次横扫会被算成一个单位、广度维度直接失效;而 `~/.claude`、
  `~/.ssh` 这类点目录本身是一个整体资产,只取一层。

## 已知边界

- 冻结只作用于**被 infsec 监督的进程树**。不经 `infsec run` 启动的进程
  不在覆盖范围内——这正是 M6(eBPF LSM 系统级)要解决的问题,
  `panic` 的检查清单第 1 条已如实提示用户手动确认。
- `panic` 与 `thaw` 按 SO_PEERCRED 的 uid 授权,只能操作自己的进程。
- 冻结登记簿在 daemon 内存里;daemon 重启后登记丢失,被冻结的进程仍是
  T 状态,需要手动 `kill -CONT`。持久化留到 M7 与审计查询一起做。
