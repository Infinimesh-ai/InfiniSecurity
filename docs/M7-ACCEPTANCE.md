## 解锁通道的设计与验收范围

解锁是整个系统里**唯一能放宽防护的通道**,约束因此最严:

- **确认必须由人在真终端上敲。** daemon 侧检查调用者有控制终端且不在
  被监督进程树内(被监督的 Agent 不能批准自己);客户端侧要求
  `isatty(stdin)` 与 `isatty(stdout)` 同时成立,并逐字输入一条随机生成的
  确认短语。脚本、管道、expect 都无法预知短语。
- **一次性、限时、不批发。** 票据只对一条具体的绝对路径 + 一个操作类别
  有效;目录前缀不认,同目录下的其他操作不受影响;用过即废。
- **没有旁路参数。** 没有 `--yes`、`--force`、`--non-interactive`,
  以后也不会加。

**验收范围的诚实说明(AGENTS.md 纪律 2):自动化验收只覆盖驳回路径。**
"批准"路径无法、也不应该被脚本验证——用 expect 去喂确认短语等于亲手
拆掉这道闸门,并且会让这项验收失去意义。批准路径需要人在真终端上手工
验证一次:

```bash
infsec unlock remove /绝对/路径/到/某个/fixture文件
# 按提示逐字输入短语
```

## `infsec boundary` 为什么值得单独做一条命令

事故当天最费时间的一步是确定"删除从哪一刻开始"——那决定了哪些数据
需要恢复、哪个时间点的备份是干净的。它应该是一条查询,不是一次考古。
现在它扫审计日志找**第一条被实际放行的删除**(exec 事件不算,签名层
拒绝的也不算),并把结果指向隔离区。

## 已知边界

- 桌面通知需要目标用户有活动的 DBus 会话(`/run/user/<uid>/bus`);
  没有就静默跳过。**通知失败绝不影响判决**——这是尽力而为的通道,
  不是判决链路的一环。
- 解锁票据存在 daemon 内存里,daemon 重启即失效(这是安全的方向)。
- 票据签发后如何被判决层消费,接口已在 `unlock::TicketBook` 就位并
  单测覆盖,但尚未接入 pipeline 的 `ReviewMode::Human` 分支——
  当前 `human` 复核仍一律 fail-closed 拒绝。这是保守的缺口,不是漏洞。
